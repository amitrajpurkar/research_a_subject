# Documenting Architecture in the AI Era: A Practical Framework

*Application → System → Enterprise, optimized for both AI consumption and human/business readability*

---

## 1. The core problem you're solving

Three audiences, three different needs, one source of truth:

| Audience | Wants | Format that works |
|---|---|---|
| AI tools (Claude, Copilot, RAG pipelines) | Structured, parseable, unambiguous, co-located with code | Markdown + YAML frontmatter, diagrams-as-code (text, not binary images) |
| Engineers | Precision, traceability to code, low maintenance overhead | Docs-as-code, generated where possible, versioned with the repo |
| Business/IT stakeholders | Visual, layered, jargon-free at the top | Same source, rendered at different zoom levels (not a separate Visio deck) |

The mistake most orgs make: maintaining a Visio/PowerPoint architecture deck that's disconnected from the code and rots within a quarter. The fix is **diagrams-as-code + docs-as-code**, so architecture lives next to what it describes, gets reviewed in pull requests, and can be regenerated instead of manually redrawn.

---

### The prompt provided

```
in todays era of AI tools, in the context of software engineering, what are the best techniques of documenting application architectures, system architectures (where each system may be comprised of multiple applications) and enterprise architectures where cross domain and cross functional systems interact with each other; the main intension is to document these architectures in such a way that it helps AI tools to use as input sources as well be easy for humans to understand and be visually appealing to every human. stake-holders in IT and Business teams; Also make note of another common fact that most of the application code is under version control systems, but at same time database and data model/ data structure knowledge is known to humans; so also system configurations as well are known typically to humans
```

## 2. Use a layered model, not one big diagram

The single best mental model for the three levels you named is the **C4 model**, extended upward with **ArchiMate/TOGAF concepts** for the enterprise layer.

```
Level 1 — System Context     "How does this system fit in the world?"
Level 2 — Container          "What are the deployable/runnable pieces?" (apps, services, DBs)
Level 3 — Component          "What's inside a container?"
Level 4 — Code               (usually auto-generated from code, not hand-drawn)
```

Map this to your three scopes:

- **Application architecture** → C4 Levels 2–3 for a single application/service
- **System architecture** (multiple apps forming a system) → C4 Level 1–2, one Context diagram per system, one Container diagram showing how its constituent apps talk to each other
- **Enterprise architecture** (cross-domain, cross-system) → a **Landscape/Capability diagram** (ArchiMate-style) sitting *above* C4 Level 1 — showing which systems exist, which business capability/domain owns them, and the integration contracts between them (not their internals)

This gives you **one consistent zoom-in path**: an executive can look at the enterprise landscape, click into a system context diagram, click into a container diagram, click into a component diagram — without maintaining four disconnected documents.

---

## 3. Make every diagram text-based ("diagrams-as-code")

This is the single highest-leverage practice for your stated goal (AI-readable + human-visual + version-controllable):

| Tool | Best for | Why it fits |
|---|---|---|
| **Mermaid** | Flowcharts, sequence diagrams, ER diagrams, C4-lite | Renders natively in GitHub/GitLab/Notion/Obsidian; plain text; trivial for an LLM to read *and* generate |
| **Structurizr DSL / C4-PlantUML** | True C4 model (Context/Container/Component) with consistent notation | Purpose-built for the C4 levels above; can auto-export to multiple formats |
| **PlantUML** | Sequence, component, deployment diagrams | Mature, scriptable, good CI integration |
| **ArchiMate (via Archi tool, exportable to XML)** | Enterprise-level capability/domain maps | Standard notation business architects already recognize |
| **OpenAPI / AsyncAPI specs** | Interface contracts between systems | Machine-readable AND renders as human-friendly docs (Swagger UI, Redocly) |

Because these are plain text, they:
- Live in the same Git repo as the code → version controlled, PR-reviewable, diffable
- Are trivially ingestible by AI tools (an LLM can read Mermaid/PlantUML source directly — no OCR, no screenshot parsing)
- Can be regenerated as SVG/PNG for stakeholder decks with zero manual redrawing
- Can literally be **generated by AI** from a description, and **kept in sync by AI** during code review (a growing pattern: a CI check that asks an LLM "does this diagram still match the code change?")

**Avoid**: Visio, draw.io binary files (unless exported to their `.drawio` XML alongside a rendered PNG), Lucidchart-only diagrams, or anything living only in a slide deck. These are dead ends for AI tooling and drift silently.

## 4. Structure the written documentation: arc42 + ADRs + C4 narrative

Diagrams alone aren't enough — reviewers and AI tools both need the *why*, not just the *what*.

**For application/system level**, use the **arc42 template** (or a trimmed version of it). It's a proven, boring, well-known skeleton:

```
1. Introduction & Goals
2. Constraints
3. Context & Scope        → Level 1 diagram lives here
4. Solution Strategy
5. Building Block View     → Level 2/3 diagrams live here
6. Runtime View            → sequence diagrams for key flows
7. Deployment View
8. Cross-cutting Concepts  (security, auth, error handling, observability)
9. Architecture Decisions  → link to ADRs, don't inline them
10. Quality Requirements
11. Risks & Technical Debt
12. Glossary
```

**Architecture Decision Records (ADRs)** are non-negotiable in this era. One short markdown file per significant decision:

```markdown
# ADR-014: Use Kafka for Care Connect ↔ Jiva event sync
Status: Accepted | Date: 2026-03-12
## Context
## Decision
## Consequences
## Alternatives considered
```

Why ADRs matter specifically for AI tooling: they give an LLM the **rationale trail**, not just the current state. When someone asks "why does this integration work this way," an LLM grounded on ADRs answers correctly instead of guessing from the diagram alone. Store them as `docs/adr/NNNN-title.md`, sequential, immutable once accepted (superseded, not edited).

**For enterprise level**, a lighter structure works better than full TOGAF ADM ceremony unless your org already runs formal EA governance:

```
- Capability Map (business capabilities → owning domain/system)
- System Inventory (one entry per system: owner, domain, lifecycle stage, tech stack, criticality)
- Integration Catalog (system A → system B: protocol, data exchanged, direction, SLA, contract doc link)
- Domain boundary diagram (bounded contexts, similar to DDD context maps)
```

## 5. Making it genuinely AI-ingestible (not just "written in markdown")

Text isn't enough on its own — structure matters for retrieval and reasoning quality:

1. **YAML frontmatter on every doc** — gives any RAG/AI tool structured metadata without parsing prose:
```yaml
---
system: Care Connect
domain: Care Management
owner_team: Care Management Platform
tech_stack: [Java, PostgreSQL, Kafka]
depends_on: [Jiva, EIS]
last_reviewed: 2026-06-01
---
```
2. **One concept per file, predictable naming** — `systems/care-connect/context.md`, `systems/care-connect/container.md`, `systems/care-connect/interfaces/jiva-sync.md`. AI tools (and humans) navigate a predictable tree far better than one 40-page doc.
3. **Explicit, not implied, relationships** — write "Care Connect publishes `MemberEnrolled` events consumed by Jiva" rather than relying on a diagram arrow alone. Diagrams communicate to humans at a glance; the accompanying sentence is what an LLM actually indexes reliably.
4. **A single machine-readable system registry** (even a simple YAML/JSON catalog, or a proper tool like **Backstage**) that enumerates every system, its owner, its repo, its docs location, and its dependencies. This is the file an AI agent should be pointed at first — it's the index into everything else.
5. **Co-locate docs with code** (`/docs` folder per repo, or a docs monorepo mirroring repo structure) so an AI coding tool reading the repo naturally has architecture context in-frame, not in a separate wiki it can't see.

## 6. Your specific concern: what's *not* in version control

You flagged three things correctly — code is versioned, but DB schemas, data models, and system configuration usually live only in people's heads or in the running systems themselves. Treat each differently:

### Database / data model
- **Generate, don't hand-draw.** Tools like `dbt docs`, **SchemaSpy**, **dbdocs.io**, or `pg_dump --schema-only` piped into an ER-diagram generator (Mermaid ER syntax, or `mermaid-erd`) turn the live schema into version-controlled, always-accurate text.
- Commit the generated schema-as-code (DDL, or a dbt/Liquibase/Flyway migration history) to the repo. This instantly becomes both the source of truth *and* AI-readable *and* diffable.
- If schemas evolve outside migration tooling (common in older healthcare platforms like Jiva), schedule a periodic **schema snapshot job** that dumps current DDL to a `schema/` folder in a docs repo — even read-only capture beats nothing.

### System configuration
- Where possible, move to **config-as-code** (Infrastructure as Code, Helm values, `.env.example` files, Terraform) — this is the real fix, not documentation.
- Where that's not feasible short-term (legacy platforms, vendor-managed systems like EIS), maintain a **configuration inventory doc** per system: key settings, environment differences, who owns changes, last-verified date. Treat it like an ADR — dated, owned, reviewed on a cadence — rather than a stale wiki page nobody trusts.

### General principle for "tribal knowledge" capture
Run periodic **architecture capture sessions** (you already do something like this with your Granola → Notion pipeline) specifically aimed at externalizing what's only in someone's head — DB quirks, config gotchas, integration edge cases — straight into the versioned docs structure above, not into a separate meeting-notes silo.

## 7. Making it visually appealing to *every* stakeholder (not just engineers)

The trick is **one source, multiple renderings** — not separate artifacts per audience:

- **Executives/Business**: auto-render the enterprise capability map and system landscape diagram only — hide container/component detail. Keep to ≤15 boxes, plain business language, no protocol names.
- **IT/Product stakeholders**: system context + container diagrams, with the integration catalog table alongside.
- **Engineers**: full C4 stack down to component level, ADRs, schema docs, runtime sequence diagrams.

Practically: keep everything in Mermaid/Structurizr source, and use a **static site generator** (Structurizr's own workspace renderer, Backstage TechDocs, or even a simple MkDocs/Docusaurus site built off the same markdown+Mermaid) to publish different "views" or navigation entry points from the same underlying files. Given your existing Notion-centric workflow, you could also mirror rendered diagrams into a Notion page per system as the "business-friendly" front door, while the markdown+Mermaid source remains the versioned source of truth in Git.

## 8. Minimal toolchain to start with (pragmatic, not maximal)

| Layer | Tool |
|---|---|
| Diagrams | Mermaid (fast start) → Structurizr DSL (once you want strict C4 discipline) |
| Decisions | ADRs as markdown in `docs/adr/` |
| App/system docs | arc42-lite markdown template per system |
| Enterprise catalog | A single YAML/JSON system registry (or Backstage if you want a real portal) |
| DB schema | Auto-generated via dbt docs / SchemaSpy, committed to repo |
| Config | IaC where possible; dated config-inventory doc where not |
| Publishing | MkDocs/Docusaurus or Backstage TechDocs, built from the same markdown |

Start with just **Mermaid + arc42-lite + ADRs + a YAML system registry**. That alone gets you 80% of the value — text-native, git-versioned, AI-ingestible, and renderable for any stakeholder — without adopting a heavyweight EA suite up front. Layer in ArchiMate/Backstage/Structurizr once the lightweight version proves itself and governance needs grow.
